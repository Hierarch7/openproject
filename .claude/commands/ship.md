## Цель

Выполнить полный цикл: ревью → фикс → браузерная проверка → code/security review → линтеры и тесты → коммит → итоговый отчёт. Каждый шаг выполняется строго после завершения предыдущего.

Флоу **заканчивается коммитом**. Пуш и создание PR — вручную пользователем (CI форка `Hierarch7/openproject` не запускается: `test-core` гейтится `github.repository_owner == 'opf'`, `continuous-delivery` — `github.repository == 'opf/openproject'`, а `rubocop-core`/`eslint-core`/`erb-lint-core` висят только на `pull_request`).

## User Input

```text
$ARGUMENTS
```

Если пользователь передал аргументы — учесть их как дополнительный контекст (например, scope коммита или на что обратить внимание при ревью).

## Шаг 1: Проверь диф

Запусти `git diff` (и `git diff --cached` если есть staged изменения). Проведи ревью:

- Не ломает ли логику, есть ли edge-cases
- **Авторизация**: не обойдены ли проверки прав — контракты (`app/contracts/`), политики (`app/policies/`), permissions. Новый эндпоинт/действие без проверки прав = блокер
- **Запросы**: N+1, отсутствующие `includes`/`preload`, тяжёлые выборки без индексов
- **Слои**: бизнес-логика в сервисах (`app/services/`, возвращают `ServiceResult`), контроллеры тонкие, валидация и авторизация в контрактах
- **i18n**: нет захардкоженных UI-строк — только ключи перевода (`config/locales/en.yml`, для фронта `config/locales/js-en.yml`, для модулей `modules/*/config/locales/en.yml`)
- **UI-слой**: ViewComponent + Primer для переиспользуемых компонентов, Hotwire (Turbo + Stimulus) для интерактивности. Новый Angular-код — только если расширяется существующий legacy-компонент; иначе это шаг назад от текущей миграции
- **Миграции**: обратимость, индексы, влияние на большие таблицы
- **Модульность**: код модуля живёт в `modules/<name>/`, не протекает в core

**Формат вывода — только список замечаний, без кода.** Разбей по приоритетам:

- **HIGH** — блокеры мержа
- **MED** — починить сейчас если быстро
- **LOW** — мелочи / косметика

Для каждого пункта:

- Краткая причина
- Стратегия фикса (1–2 предложения)
- Нужен ли тест и какой сценарий (RSpec: `spec/models/`, `spec/services/`, `spec/requests/`, `spec/features/` для Capybara; фронт: `ng test`)

Не overengineering — не предлагать рефакторинг ради рефакторинга.

**Важно**: не отклонять и не ставить замечания на изменения, которые пользователь внёс осознанно (бизнес-логика, новые фичи, архитектурные решения). Ревью должно ловить баги, уязвимости и технические проблемы — а не оспаривать намерения автора.

**После вывода замечаний — НЕ останавливайся, сразу переходи к Шагу 2.**

## Шаг 2: Исправь всё

Проанализируй все найденные на Шаге 1 замечания уровня HIGH и MED и исправь их **по порядку**.

Принципы:

- Не быстрые заплатки — **корректные, продуманные, надёжные решения** (best practices)
- Без лишних деталей и объяснений — сразу к делу
- **Использовать существующие паттерны проекта**, а не изобретать свои. Смотреть sibling-файлы. Монорепа большая — почти для любой задачи уже есть образец
- Соблюдать конвенции из вложенных `CLAUDE.md` (`app/CLAUDE.md`, `spec/CLAUDE.md`, `docker/dev/CLAUDE.md`)
- Если в коде есть несовершенства — применять более продвинутые подходы
- При необходимости — провести веб-поиск или задать вопрос пользователю (до 3 вопросов)

Обязательные требования к правкам:

- Новые UI-строки — **только через ключи перевода**, добавленные в `en.yml` (и `js-en.yml` для фронта). Непереведённые/осиротевшие ключи ловятся `spec/i18n_spec.rb` и workflow `i18n-tasks`
- Сервисы возвращают `ServiceResult`; авторизация и валидация — в контрактах, не в контроллере
- Новые ViewComponent'ы — с Lookbook-превью (`lookbook/`), как у соседних компонентов
- Миграции обратимы (`change` или парные `up`/`down`)
- Изменения модуля остаются внутри `modules/<name>/`

LOW-замечания: исправить только если это занимает < 1 минуты, иначе пропустить.

**После исправлений — сразу переходи к Шагу 3.**

## Шаг 3: Браузерное тестирование

Проверить изменённые фичи в браузере через **Playwright MCP** (дефолт для UI-задач; Chrome DevTools MCP — только для perf/Web Vitals/Lighthouse).

Если изменения **чисто бэкендовые** (сервис/миграция/воркер без UI-поверхности) — шаг пропустить, указав причину в отчёте.

### Предварительная проверка

1. Убедиться что локальный сервер запущен — открыть `http://localhost:3000` через `browser_navigate`.
2. Если сервер не отвечает — **остановиться и попросить пользователя запустить** `bin/dev` (или `bin/compose start` для Docker-окружения). Не пытаться запускать сервер самостоятельно: подъём Rails + Angular + good_job долгий и шумный.

### Логин

- Дефолтный сид-админ OpenProject: **login `admin`**, **password `admin`** (при первом входе инстанс может потребовать смену пароля).
- Если креды не подходят — **спросить у пользователя**, не подбирать.
- Авторизоваться через `browser_fill_form` / `browser_type` + `browser_click`.

### Тестирование

1. **Определить scope**: какие страницы/фичи затронуты изменениями (на основе дифа из Шага 1).
2. **Навигация**: перейти на затронутые страницы, авторизоваться если нужно.
3. **Визуальная проверка**: `browser_take_screenshot` — убедиться что страница рендерится без ошибок.
4. **Консоль**: `browser_console_messages` — нет ли JS-ошибок. Warnings от legacy Angular-слоя допустимы, ошибки — нет.
5. **Функциональная проверка**: если затронуты интерактивные элементы (формы, Turbo-фреймы, Stimulus-контроллеры, фильтры) — протестировать через `browser_click`, `browser_type`, `browser_fill_form`. Turbo-навигация не должна ронять страницу в полный перезагруз.
6. **Сетевые запросы**: если затронут API (`/api/v3/...`) — проверить `browser_network_requests` на 4xx/5xx.

### Критерии прохождения

- Страница рендерится без ошибок
- Нет JS-ошибок в консоли (warnings допустимы)
- Изменённая функциональность работает корректно
- Нет сломанных сетевых запросов

**Если найдены проблемы** — исправить и вернуться к Шагу 2 для повторной проверки.

### Закрытие браузера (обязательно)

После завершения проверки — **закрыть браузер** через `browser_close`, чтобы освободить его для других сессий. Браузер один на всех агентов: оставленный открытым — блокирует параллельные сессии.

- Закрывать **в любом случае**: и при успешной проверке, и при найденных проблемах (перед возвратом к Шагу 2).
- Если после фикса нужна перепроверка — открывать браузер заново через `browser_navigate`.

**После успешного браузерного тестирования и закрытия браузера — переходи к Шагу 4.**

## Шаг 4: Code review + Security review

Перед коммитом фича обязана пройти два ревью:

1. **`/code-review`** — ревью дифа на корректность, edge-cases, авторизацию, N+1, слоистость (сервисы/контракты/контроллеры).
2. **`/security-review`** — проверка на уязвимости (инъекции, обход авторизации и permissions, утечки данных между проектами, XSS в ERB/Angular-шаблонах, небезопасная работа с вложениями).

Порядок:

- Запустить оба ревью по текущему дифу.
- **Исправить все находки** уровня HIGH/MED (LOW — по усмотрению, см. Шаг 2). Исправления делать по принципам Шага 2.
- Если ревью выявило проблемы, требующие браузерной перепроверки — вернуться к Шагу 3.

**После прохождения обоих ревью и исправления находок — переходи к Шагу 5.**

---

## Шаг 5: Линтеры и тесты

Прогнать проверки **до** коммита (см. `CLAUDE.md` → «Linting (Run Before Committing)»). Часть из них lefthook и так запустит на pre-commit по staged-файлам — но упавший хук ломает коммит уже после подготовки сообщений, дешевле поймать заранее.

Запускать **только по затронутым областям**, не весь набор:

- **Ruby**: `bin/dirty-rubocop --uncommitted`
- **JS/TS**: `cd frontend && npx eslint <изменённые файлы>`
- **ERB**: `erb_lint <изменённые .erb>`
- **RSpec** (целевые файлы, не полный прогон): `bundle exec rspec spec/path/to/relevant_spec.rb`. В Docker — `bin/compose rspec spec/...`
- **i18n**: если добавлялись/менялись ключи перевода — `bundle exec rspec spec/i18n_spec.rb`
- **Фронт-юниты**: если менялся Angular-код — `cd frontend && npm test`

Падения чинить по принципам Шага 2 и перезапускать проверку. Если тест падает по причине, не связанной с изменениями (флейки, окружение) — зафиксировать это для отчёта и не чинить чужое.

**После зелёных проверок — переходи к Шагу 6.**

---

## Шаг 6: Коммит

Выполнить коммит по разделу **`## Commit Messages` в `CLAUDE.md`**: первая строка < 72 символов, пустая строка, затем подробное описание; ссылка на work package если применимо.

Ship-специфика:

- **Коммитить БЕЗ подтверждения пользователя** — вызов `/ship` уже авторизует цикл до коммита включительно. Кратко показать предложенную структуру коммитов и сразу выполнить.
- Проверить untracked-файлы перед коммитом — новые файлы легко потерять.
- Коммитить **только свои файлы** изолированно. В рабочей копии могут висеть посторонние изменения (например `frontend/package-lock.json` или дописанный тулингом `AGENTS.md`) — не тащить их в коммит фичи.
- **Группировать по смыслу**: одна группа = одна фича / один модуль. Группа может состоять из нескольких коммитов (бэк + фронт + тесты одной фичи), но один коммит не должен покрывать две несвязанные фичи. Группы понадобятся для отчёта в Шаге 7.
- **Не пушить.** Флоу заканчивается коммитом — push и PR остаются за пользователем.

**После коммитов — переходи к Шагу 7.**

## Шаг 7: Итоговый отчёт

Финальный вывод пользователю по завершении всего цикла. Две части подряд.

### Часть A — Отчёт по фазам

Компактная сводка по каждой пройденной фазе: **фаза → что найдено/сделано → результат**. Формат — таблица или маркированный список, одна строка на фазу. Пропущенные фазы отметить как «—» / «пропущено» с причиной (напр. «Шаг 3 пропущен — чисто бэкендовые изменения, UI не затронут»).

Ориентир по строкам:

- **Ревью дифа (Шаг 1)** — сколько замечаний по приоритетам (напр. `1 HIGH, 2 MED, 0 LOW`).
- **Исправления (Шаг 2)** — что исправлено / «замечаний не было».
- **Браузер (Шаг 3)** — что проверено, результат (рендер ок, консоль чистая) или причина пропуска.
- **Code + Security review (Шаг 4)** — находки и что исправлено / «чисто».
- **Линтеры и тесты (Шаг 5)** — что прогнано и результат; отдельно отметить падения, признанные не связанными с изменениями.
- **Коммит (Шаг 6)** — сколько коммитов, короткие хеши, смысловые группы.

В конце строкой — напоминание, что изменения **закоммичены, но не запушены**.

### Часть B — Что сделано функционально

Краткая сводка (3–6 пунктов) сути изменений **с точки зрения функциональности/пользователя**: что теперь работает иначе, какая проблема закрыта, какое поведение добавилось. Логически, **без имён файлов, методов, классов**. Это ответ на вопрос «что реально изменилось в продукте», а не «какие строки правились».

Тон — по правилам проекта (кратко, по делу, на русском). Не повторять поштучно то, что уже в таблице фаз.
